## Why provenance code is needed for `run_permutation_search.py` itself

The lineage system tracks two *different* objects, not one:

1. **The result file's provenance** — for `permutation_search_summary.json`, this is "which script, with which inputs, on which compute job produced this JSON." That's answered by the job-dispatch record (the `submit_job` call: command, inputs, intent) — it says *"run_permutation_search.py was executed with these arguments and wrote this file."*
2. **The script's own provenance** — for `run_permutation_search.py` itself, this is a separate question: *how did this exact version of the code come to exist.* Scripts in this pipeline were revised repeatedly in response to specific reviewer items (the docstring literally opens with "reviewer item 1.2: permutation calibration of the SEARCH"), so a later edit could silently change what an earlier results file actually represents. Without independently tracking the script artifact's own history, there'd be no way to confirm that the `run_permutation_search.py` version that generated a given `permutation_search_summary.json` is the version currently in `paper_v4`'s citation trail — a later bugfix to the script wouldn't automatically invalidate or re-flag a stale JSON generated by an older version.

So: the JSON's provenance answers "what generated this data," and the script's own provenance answers "what generated this code" — auditing correctness requires being able to answer both independently.

## Full order of operations, starting from `harmonise.py`

**0. Reconnaissance (precedes the pipeline proper)**
`probe_env.py` → `probe_data.py` → `probe_cohorts.py` — confirm remote packages/columns and inspect the cohort store before committing compute.

**2. Participant-flow accounting**
